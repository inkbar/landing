Inkbar writes a session's annotations and changed form values into the PDF. Download, Print and `doc.save()` then give a file that looks as it does on screen, and other programs can read what was added. Open that file in Inkbar again and its annotations come back ready to edit.

Inkbar's engine, a build of PDFium that runs in the browser, writes the file. It is the same engine that reads and draws every file, so there is nothing to install or turn on: the engine's files come with the [assets](/docs/loading-assets/) you already pass.

The download and print buttons, Ctrl or Cmd+S and Ctrl or Cmd+P hand over the file with the session's changes written into it. `doc.save()` resolves with the same bytes.

With no changes, a save gives the bytes the file was opened from. With changes, it writes through the document's engine, so that engine must be running: while the viewer has [stopped working](#when-the-viewer-stops-working), `doc.save()` rejects with `EngineUnavailable`. `doc.getData()` always gives the bytes the file was opened from.

`doc.changed` is a readable that is true while the session differs from the file: its annotations from those it opened with, or a form value from the file's. The file's values are the ones the form holds when `ready` resolves. A value you set after that is a change, and so is one you pass at open.

## Opening documents yourself

A host that calls `openDocument` itself passes one more option, `pictures`. In a browser, `savePictures(document)` from `@inkbar/core/dom` supplies it. `createViewer` and the framework packages pass it for you.

```ts
import { openDocument } from '@inkbar/core'
import { savePictures } from '@inkbar/core/dom'

const doc = await openDocument(file, {
  assets,
  pictures: savePictures(document),
})
```

`pictures` gives a save three things from the browser: a picture of each line of text the standard fonts cannot set, a PNG copy of an image that is neither PNG nor JPEG, and the text widths the screen uses. Without it, a save lays text out with the standard fonts' own widths, so a line can break at a different word in the file than on screen. A text box with Chinese, Arabic or emoji text then fails the save with `SaveFailed`, and so does a stamp whose image is WebP.

## What goes into the file

- Each annotation becomes a standard PDF annotation that other programs can list, select and delete. A highlight is a Highlight, a note a Text annotation, a text box a FreeText and a drawing an Ink annotation. A loupe or a mask becomes a Stamp. A comment goes in the annotation's contents, and replies are saved as replies.
- Each annotation's look is drawn from the same description the screen uses, so it matches what you see in Inkbar, apart from [the differences below](#where-the-saved-file-differs-from-the-screen).
- Changed form values. Fields you did not change keep the look they came with.
- A redaction mark becomes a Redact annotation. A save does not apply it.

:::caution
Saving does not redact. The text and images under a redaction mark are still in the saved file, and anyone can copy them. Applying the marks removes them: see [Redaction](/docs/guides/redaction/).
:::

An encrypted file keeps its password. The open document holds the password until it closes, because a save, and a restart after the engine stops, open the file again in the engine.

### Signed files

A file with a digital signature is saved by appending the changes after the signed bytes, so the signature still verifies. Other viewers report that the file changed after signing. Any other file is rewritten.

Appending keeps the earlier versions of a signed file inside it. If you delete or edit an annotation that an earlier Inkbar save wrote into a signed file, a reader can still recover the old one from the earlier version. A rewrite drops it.

### Loupes

A saved loupe holds a copy of its whole page's content, fonts and images included, and shows the part under the lens. If you redact that page later in another tool, the original content stays in the file inside the loupe. When Inkbar [applies redactions](/docs/guides/redaction/), every loupe it writes gets a copy of the redacted page. A loupe that stays locked keeps its old copy, and the apply then fails ([the limits](/docs/guides/redaction/#limits) say what to do). On a page with large images the copy also adds to the file's size.

## Opening a saved file

Annotations Inkbar saved come back as session annotations, with the same ids, ready to edit. Saving again replaces them, so each one is in the file once. They are not an undo step and do not count as a change.

They arrive a moment after `ready`, as one `replace` change with `reason: 'file'`. Until then the file's copy shows, locked. A signature saved on a signature field comes back on the field, and the field shows as signed.

In [controlled mode](/docs/guides/controlled-mode/), `onChange` proposes them once, with `reason: 'file'`: your list with the saved annotations added. Apply that proposal as you apply any other, by pushing the list back. Until you push a list, the viewer does not show the saved annotations, and each save still keeps them in the file. The framework packages' undo history takes your answer as its starting point, so undo does not remove them.

Some annotations stay locked:

- Annotations made by other programs, except unapplied Redact annotations (see below).
- An annotation Inkbar saved that another program has since moved, edited, replied to or given a pop-up window. Inkbar's own replies to a note that stays locked stay locked with it.
- Inkbar's own annotations in an encrypted file.

An unapplied Redact annotation from another program opens as an editable redaction mark. It looks like Inkbar's own marks and counts in the [apply confirmation](/docs/guides/redaction/). The mark keeps its area, fill colour and overlay text. The apply draws that text as it draws the text of Inkbar's own marks, so the other program's font, size and repeat setting do not carry over. A save with changes, or an apply, removes the other program's copy and its pop-up window from the file and writes Inkbar's mark.

Such a mark stays locked in three cases:

- The file is encrypted.
- Another program's annotation replies to it.
- Its pop-up window is not listed on the same page, or does not name the mark as its parent.

The page draws a locked mark as the other program left it, and the apply skips it and counts it in `foreignMarks`.

## Where the saved file differs from the screen

- Text with characters outside the standard fonts, such as Chinese, Arabic or emoji, is saved as a picture of the line, at four pixels per point. It blurs at high zoom and cannot be selected. The annotation's contents keep the text.
- The standard fonts (Helvetica, Times and Courier) are not embedded, so each viewer draws them with its own equivalent. Widths match, and letter shapes can differ slightly.
- A note's drop shadow is not saved.
- A loupe in the saved file magnifies the page's content only. It leaves out the annotations and form fields under it.
- Form fields look as the engine draws them, which can differ from how Inkbar draws them on screen.
- Another viewer may redraw an annotation its user edits there.
- The file grows a little each time it is saved and opened again: about 1.5 KB for a file with eighteen annotations. Saving several times in one session does not add to it.

XFA forms are not supported.

## When a save fails

When the engine cannot write the file, `doc.save()` rejects with `SaveFailed`:

- `details.stage` is `'write'`: the engine could not open or write this file, or an annotation could not be drawn for it.
- `details.annotation` holds an annotation's id when that annotation is the cause.

Download and Print then hand over nothing. The viewer says why in its message box, and your error handler (`onError`, or the `error` event in Vue) hears the error.

While a copy is being written, the download and print buttons show they are busy, and another press does nothing. Inkbar keeps the written copy until the next change, so Print after Download does not write the file twice.

The three messages are `saveFailed`, `saveUnavailable` and `preparingFile`, in the `viewer` group. [Translations](/docs/guides/translations/) shows how to change them.

## When the viewer stops working

The engine runs in a worker. If it stops while a file is open, Inkbar starts a new one and opens the file in it again, and the reader sees nothing. When that fails, or the engine has stopped three times within 60 seconds, the document is stopped: `doc.engineStopped`, a readable, is true, every read rejects with `EngineUnavailable`, and the status stays `ready`.

The viewer then shows a notice over the pages: "The viewer stopped working. Your changes are kept.", with a Try again button. While it is up, annotating pauses, but scrolling, zooming and the sidebars keep working, and pages already drawn keep their image. A save with changes and an apply of redactions fail with `EngineUnavailable`, and the download and print buttons say saving is not available. Your error handler (`onError`, or the `error` event in Vue) hears `EngineUnavailable` once each time the document stops.

Try again calls `doc.restartEngine()`, which you can also call from your own code. It starts a new engine and opens the file in it again, resolving once the document reads again and rejecting with `EngineUnavailable` when it does not. Either way the session's annotations, form values and history stay as they were.

The notice's words are `engineStopped`, `engineRetry` and `engineRestarting`, in the `viewer` group. [Translations](/docs/guides/translations/) shows how to change them.

## Keeping a session outside the file

You can also keep a session without writing into the PDF. Store the annotations and form values as JSON in your own backend and import them on the next open: [Annotations](/docs/guides/annotations/#saving-annotations) and [Forms](/docs/guides/forms/#save-values-as-gloss) show how.
